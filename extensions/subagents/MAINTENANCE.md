# Subagents maintenance contracts

Task-scoped obligations for the runtime owned by [AGENTS.md](AGENTS.md). Read every section triggered by the change; cross-cutting work can trigger several branches. Inline ownership, authorization, drain, durable safety, and verification contracts continue to apply.

## Native Agent lifecycle

[README](README.md#concurrency) covers pools; [session resume](README.md#features) and [turn limits](README.md#graceful-max-turns) cover user behavior.

- `src/agent-tool.ts` and `src/result-tools.ts` own complete tool definitions; `src/agent-result.ts` shares foreground/retrieval/resume report semantics. `src/graph/result-observer.ts` owns graph-result subscribers; graph runtime owns their task lookup and terminal signaling.
- `src/structured-output.ts` owns session-keyed capture storage (`rememberStructuredCapture`/`takeStructuredCapture`), retry/repair (`repairStructuredOutput`), and failure formatting (`structuredFailure`).
- Terminal sessions remain resumable for 15 minutes in the current parent session; switch, reload, or shutdown may clean them sooner.
- Interruption provenance is typed and execution-local: only an explicit human UI stop may claim user action. Generic parent signals and programmatic RPC stops are caller cancellations; lifecycle, idle supervision, supervision ceiling, turn cutoff and unknown SDK abort remain distinct. Clear cause at new admission, retain it in immutable notifications and result details, and keep provider failure distinct from interrupted checkpoints. Fresh/resumed inline results and retrieval MUST identify unfinished work without prescribing restart. Soft turn-limit wrap-up remains distinct from hard cutoff.
- `AgentManager` owns `AgentRecord.activity` for each fresh or resumed execution; queued fresh agents have no execution activity, while queued resumes retain the prior view until actual start. Activity callbacks update that state before presentation callbacks. Reset progress, active tools, response text and supervision gates per execution while retaining lifetime accounting and the SDK session; presentation observes manager state, never a separate tool-owned tracker.
- Delayed independent-agent notifications MUST capture only manager `onComplete` settlements, never infer settlement from stopped status or `completedAt`; queued cancellations complete immediately because they own no SDK execution. Snapshot result and activity before cleanup and correlate debounce, groups, cancellation and consumption to the manager's execution identity. Resume resets consumption without changing the public agent ID; an older completion MUST NOT finish a newer execution's presentation. Retrieval whose waited execution changes MUST NOT consume the replacement.
- Foreground capacity MUST remain independent of background capacity and unlimited by default; queued blocking callers MUST settle on completion, cancellation, startup failure, or shutdown. Detached spawns and foreground resume bypass the foreground pool. Background resume returns the same public ID immediately and shares the independent background queue/capacity; each resume admits a new execution identity and delivery mode, but resets activity, start time and supervision gates only when it starts. Queued or already-aborted resumes MUST settle without prompting the SDK. Active resumes retain capacity and same-session exclusion through physical drain; foreground completion is consumed inline, background completion uses the existing notification callback. Live resume preserves the session/configuration, permissions, lifetime accounting and transcript path, appending only its new messages; resume of an evicted id preserves the session file, lifetime accounting and (when the record type's transcript setting is on) the deterministic transcript path, appending only its new messages and never rewriting the file, but rebuilds configuration and permissions. Live and reopened resumes run without a turn limit; `max_turns` limits only the original spawn.
- Foreground, retrieval, and resume MUST share structured result/error, transcript, and diagnostic details.
- Every child session persists to frontmatter `session_dir` or `<agentDir>/subagent-sessions/<parentSessionId>/` (`runAgent`). Resume of an evicted id reopens that file via the history roster, rebuilt through `runAgent` under current config and policy; the runner writes a launch entry (agent id/type, isolated/skills) into the session file, and files without it are not resumable. Missing/corrupt files, removed or disabled types, and policy denials refuse. `get_agent_result` reads evicted results read-only from the file; `steer_subagent` reports not running. Graph-owned children are not in the roster.
- `get_agent_result({run_id, wait?, verbose?})` routes independent agents and live-session `agr_*` graph runs without merging registries; details discriminate `agent` and `graph`. Graph waits use runtime signaling until a committed escalation request or terminal state; aborting retrieval MUST leave execution alive. Its call header tags graph run IDs (`isGraphRunId`) with `[graph]`; agent IDs stay untagged.
- Background guidance MUST direct orchestrators to `get_agent_result({run_id, wait:true})`, NEVER end the turn while work runs, and NEVER suggest polling or idle waiting on notifications.
- Final answers at the soft turn limit MUST complete normally; unfinished tool turns receive wrap-up steering.

- Agent advertisements MUST NOT include model configuration; results report the actual model.

It is never registered, so no roster, `/agents`, `agent` call, or graph node can select it.
- Full/compact lists and custom placeholders MUST show the normalized `tools:` rules, `none` when empty, and isolation; configuration NEVER verifies runtime loading, authentication, or permissions.
- The `agent` tool description MUST be the sole configured-agent roster; `subagent_type` parameter guidance MUST NOT repeat agent names.
- While `agent` is active, `before_agent_start` MUST set the `subagents` prompt section to the current-policy hint, resolved with the same persisted delegation-policy resolution as runtime enforcement. It MUST list permitted names only and MUST NOT persist or accumulate hint messages.
- Selected candidate `:fast` fixes Fast on; no suffix fixes off, NEVER inherited/session toggles. Validate explicit on before child creation; unsupported capability MUST NOT trigger fallback selection. Preserve selected metadata through `agent`/RPC/manager/runner; direct model options MUST NOT bypass frontmatter.
- Hidden `subagent-fast` hooks MUST survive isolation/excludes and remove discovered interactive `fast` copies. Apply strict request-local metadata without shared-model mutation, including after OAuth drift; provider errors surface normally. Resume retains the original captured policy.

## Graph tools and validation

[Bundled skill](skills/agent-graphs/SKILL.md), [authoring reference](skills/agent-graphs/references/authoring.md), and [bounded-feedback reference](skills/agent-graphs/references/bounded-feedback.md) cover invocation and typed authoring.

- Agent graphs are always available: `agent_graph`, `resolve_agent_graph_gate`, `/agent-graph-replay`, graph retrieval, and graph skill discovery register at activation; there is no enable setting.
- Graph usage guidance MUST live in bundled `skills/agent-graphs/SKILL.md`, required reading before every `agent_graph` call; authoring guidance lives in its [authoring reference](skills/agent-graphs/references/authoring.md), with fanout/expand detail in its [dynamic expansion reference](skills/agent-graphs/references/dynamic-expansion.md). Discover the skill through native `resources_discover`, and NEVER advertise it through package metadata or personal skill installation. The committed [agent-graph portfolio](../../agent-graphs/) owns saved graphs.
- The graph tool description owns when to use `agent_graph` and MUST point to the resolved bundled skill; reading/invoking the skill MUST NOT grant execution opt-in. Agent roster authority remains the current `agent` tool description.
- Optional `AgentGraph.semanticPolicy` accepts `context-gather-v1` or `deep-research-v1`. `context-gather-v1` binds the `plan` / `research` bounded-feedback / `synthesize` contract explicitly, never by graph name. `context-gather-policy.ts` checks unique requested IDs before dispatch, complete in-scope plans with unique `taskId`s, in-scope evaluator tasks whose `taskId`s are unique and disjoint from plan and earlier/current iterations, research leaves (`work` stage) whose `claimId`s start with `<item.taskId>-` and whose `criterionIds` are a subset of the item's, exact unambiguous completed-claim retention, exact coverage and matching claim links, direct support and succeeded coverage through the existing structured repair seam. Restore applies the same checks to completed outputs including active evaluators and leaves (item from the work collection, else the feedback iteration's task list); the policy persists with the graph, with no implicit opt-in for older snapshots or new public research output.
- `deep-research-v1` binds `planning` (`graph`) / `research` bounded-feedback with a required `judge` / `synthesize` (`agent`), never by graph name. `deep-research-policy.ts` builds a position-ID ledger (`r<round>-<item>-<claim>`, seed = round 0) from saved results only and rewrites only admitted evaluator and judge `feedback`, writer `research` references and iteration-2+ work prompts (templates unchanged). `skipsJudge` is the deterministic route: while a plan part lacks a primary ledger claim, the iteration skips the judge and materializes the evaluator directly. At the repair seam the policy rejects evaluator tasks for a gap that already had two tasks without a closing claim, directing the evaluator to keep that gap and return `tasks []` when no other task remains, and rejects writer citations, URLs or coverage outside the ledger/plan. Restore reapplies these checks and the same route. The [bounded-feedback reference](skills/agent-graphs/references/bounded-feedback.md#deep-research-v1) owns the ledger shape.
- Edge `when` ValueRefs MUST fail validation only when the path provably cannot exist: a closed object level (`additionalProperties: false`, no combinators/`patternProperties`/`$ref`) lacks the property, or the path descends below a scalar; indexes descend only through single-schema `items`. Decision gates check their question-derived output schema; refs without `node` check a closed graph `inputSchema`. Open, combinator, or missing schemas NEVER error; node `input` and `outputs` ValueRefs are not path-checked.
- An `agent` repair respawn (execution sequence > 1) MUST append `Previous attempt <n-1> failed:` with the last 2000 failure characters and `Return a corrected result.` to the prompt; attempt 1 is unchanged. This memory is actor-local: restored executions use the original prompt, and NODE/COORD protocol, receipts, ledger, checkpoints and history are unchanged.
- Saved graph resolution accepts `.graph.json` and `.graph.yaml` through the same validation/runtime path. Roots remain ordered `.pi/agent-graphs`, `agent-graphs`, `.agents/agent-graphs`, then the global agent directory; same-name formats within one root fail as ambiguous. YAML accepts only JSON-compatible data, with duplicate keys, custom tags, and excessive aliases rejected.

## Root and nested actor protocols

[ADR 0004](../../docs/adr/0004-graph-actor-context-is-an-owned-mutable-aggregate.md) defines actor context ownership; [bounded-feedback spec](../../docs/specs/agent-graph-bounded-feedback.md) covers persistence and nested checkpoints.

- `node-protocol.ts` defines production resolver-free NODE messages and immutable admission receipts. Root-owned per-incarnation journals separate prepared ACKs from committed replay and compare duplicates before current-correlation validation. Admission handoff follows checkpoint; repair atomically drains the old execution and admits its successor within the absolute budget.
- Root-owned SubgraphActor MUST explicitly own one native `graphLogic` child without adding depth. Running parent admission MUST commit before wrapper/child spawn. Nested CHECKPOINT.REQUEST and GRAPH.DRAINED MUST relay as correlated COORD checkpoint and settlement requests; immutable checkpoint data retains callback identity without cloning functions. Root retains nested validation, ordinal/history assignment, recovery, disposition and buffered publication authority. Requests continue during cancellation/drain; settlement ACK then RELEASE_READY → RELEASE → RELEASED retains wrapper/parent capacity until physical drain and committed settlement.
- Nested graphs MUST be native `graphLogic` children of SubgraphActor. Their invocation-correlated, monotonic checkpoint request/ack protocol commits through the containing root transaction before acknowledgment or publication; matching duplicate sequences are idempotent and conflicting/reordered requests fail closed. Carry root depth 0 and reject depth above 32 before child creation and recursively on restore. Panda v2 remains authoritative; NEVER persist XState snapshots.
- Inflight subgraph skip/retry MUST append a separate parent disposition bound to run/instance/activation/graph attempt and scheduler attempt before stopping children. Restore MUST drain nested effects first, then apply only a matching disposition; retries start a fresh child invocation without replaying prior controls. Cancelled snapshots MUST acquire ownership and reconcile drains before settled cleanup; unresolved validation-gate drains retain the snapshot.

## Dynamic coordinators and feedback

[Dynamic expansion reference](skills/agent-graphs/references/dynamic-expansion.md) and [bounded-feedback reference](skills/agent-graphs/references/bounded-feedback.md) cover authoring; [bounded-feedback spec](../../docs/specs/agent-graph-bounded-feedback.md) covers persistence and restore.

- `coordinator-protocol.ts` defines immutable resolver-free COORD receipts, full-operation ACKs, and root-owned prepared/committed replay journals. Expand admission (including restored running identity) commits before actor creation; expand/fanout/feedback coordinators consume no executor/resource slot but retain native ownership through explicit release or infrastructure drain.
- ExpandActor prepares source/namespace validation, requests atomic insertion or ordinary node failure, awaits the containing checkpoint ACK, then completes RELEASE_READY → RELEASE → RELEASED. Root revalidates current collisions and the 500-node effective limit before inserting definitions, edges, identities, and `{}` settlement in one checkpoint. Dynamic registrations precede updates/admission after commit.
- Restored running expands recompute authoritative resolved source without incrementing attempt/identity; committed settled expands create no actor. Whole-run cancellation commits before COORD.CANCEL and suppresses pending insertion; lifecycle cancellation preserves interrupted running evidence. Active expand skip/retry remains unsupported. Infrastructure FAIL drains without further writes. Panda v2 is unchanged.
- FanoutActor and generated leaf actors are native root siblings. FanoutActor requests atomic materialization, consumes bounded committed owner views, requests ordered all-settled aggregation, and releases only after ACK. Root validates the entire batch against current topology/run bounds, assigns definitions/UUIDs/provenance/ordinals/ownership, and checkpoints before registration or leaf dispatch. Existing collections attach without preparation or identity/attempt changes; settled owners create no actor.
- Fanout coordinators use no executor slots; root retains each leaf independently through NODE release even after collection settlement. Pause does not block active collection aggregation or drain; active ordinary fanout owner skip/retry remains unsupported and leaf controls remain available. All ordinary and feedback work collections use FanoutActor; no automatic root aggregation remains.
- FeedbackActor, every work FanoutActor, evaluator and item leaf are direct root siblings. Feedback consumes bounded committed owner views and requests initial intent, complete atomic iteration materialization, and decision transactions through COORD; both ACK and progressed committed facts precede successor requests. Root checkpoints running admission before spawn; absent-state admissions and restored active owners retain attempts/IDs. Terminal owners create no actor.
- Feedback materialization commits work/items (and the evaluator when no `judge` is declared), ownership, definitions, UUIDs, provenance/ordinals and active state together; work FanoutActor attaches without allocating. A judged iteration reserves capacity for its tasks + 3 nodes; its judge and evaluator materialize lazily as root-driven steps inside the `feedback-decision` operation, each after its predecessor settles. The feedback view reports `judging` while the judge runs and `evaluation` only once an evaluator exists. Decision/history and continuation intent commit separately before successor allocation. Whole-run cancellation atomically normalizes feedback and leaf dispositions before signaling and waits all independent drains/releases; lifecycle cancellation remains resumable. Active feedback owner skip/retry is unsupported.
- Feedback `retryFailures` counts accepted evaluator failures, not admissions or cancellations. `retryError` exists exactly when that count is positive. Same-evaluator checkpoints append at most one failure, must match newly appended failure outcomes for that exact instance, and cannot rewrite an unchanged count's error; only a new evaluator materialization resets evidence to zero. Fresh protocol-v1 restore requires the exact failure-outcome count; a deterministic legacy baseline permits only historical uncertainty bounded by that evaluator's baseline admissions, never missing post-baseline failures. Execution-ledger accounting remains the repair-budget authority.
- Loop targets MUST NOT reach `fanout` or `bounded_feedback` over normal edges, including guarded paths; expansion MUST validate the combined effective topology before atomic insertion. Restore skips authored-placeholder checks only for collection children whose exact generated definitions and ownership/UUID/provenance pass regeneration against durable templates and input.
- `fanout` MUST atomically materialize validated typed items as ordinary agent children, await every terminal child, and return input-ordered all-settled results. Generated children use stable `<fanout-id>:item:<index>` IDs and inherit fanout phase metadata.
- `bounded_feedback` owns only fixed fanout/evaluator templates, an optional `judge` decision template, typed gap-linked decisions, append-only accumulation, hard bounds and no-progress termination. The [authoring contract](skills/agent-graphs/references/bounded-feedback.md) owns schema/results and optional deadline/spend bounds; the [bounded-feedback spec](../../docs/specs/agent-graph-bounded-feedback.md) owns persistence, restore and checkpoint internals. A true judge verdict records `sufficient` without an evaluator; a false verdict materializes the evaluator, which returns only gaps and tasks, and `tasks: []` stops with `no accessible route` and partial evidence; a failed or skipped judge stops as `evaluator failure`. Deadline uses the durable run start (escalation waits count); spend sums reported USD costs of existing work, judge and evaluator nodes, including repairs, never token estimates, and checks each node's cost attempts against its model executions, so an escalation-only resume adds no cost row. Check before initial materialization, before continuation intent and before restored-intent allocation/dispatch; missing settled-execution accounting MUST stop growth with partial evidence. Restore MUST retain start/costs and fresh replay MUST start anew.

## Decision gates and escalation

[ADR 0005](../../docs/adr/0005-decision-gate-classifier-first-with-orchestrator-escalation.md) records the design; the [authoring reference](skills/agent-graphs/references/authoring.md#node-reference) covers questions and output shapes.

- `decision_gate` is the only decision node type. `decision-gate.ts` derives its exposed output schema, escalation response schema, and agent-fallback schema from its questions. `validation.gate` remains separate deterministic agent validation.
- The host walks the decision model chain inside ONE ledger execution (target `agent`): classifier entries classify, chat entries run the [internal agent fallback](#invocation-and-model-policy), failures advance, and the first valid answer decides. The decision records the aggregated chain cost once; any entry with unknown cost makes the whole cost unavailable, never a partial sum. Each entry checks abort first and drains its owned child.
- Any answer below `minConfidence` (default from `decisionGateMinConfidence` in settings) or an exhausted chain escalates. The NODE `escalate` operation commits cost and dispatch target `escalation` with a bounded reason before any request publishes, including every containing nested checkpoint. The checkpoint keeps only that reason; questions, state, and response schema regenerate from the definition and durable upstream outputs, so live and restored requests match.
- Lifecycle-interrupted escalations resume escalation-only and NEVER re-run the decision chain.
- Requests expose an opaque execution-correlated `gate_id`, activation-local `revision`, kind, reason, questions, state, and `response_schema`; repeated retrieval NEVER consumes them. Persist no additional prompts or response history.
- `resolve_agent_graph_gate({run_id, gate_id, revision, response})` takes `{answers, decidedBy: "orchestrator" | "human"}`, validated against the derived response schema and current committed execution; resolved answers carry confidence 1. Identical accepted responses are idempotent within the activation; stale or conflicting responses fail. Reload reconstructs pending requests with new revisions and rejects all pre-reload responses, including nested gates; retrieve again before resolving.
- The orchestrator decides or asks the human with `ask`, sets `decidedBy` truthfully, then resolves and retrieves again. Graph hosts NEVER call UI prompts. Unobserved escalations receive one held follow-up nudge; retrieval cancels its pending nudge without consuming the gate. Lifecycle/terminal cleanup cancels nudges and settles subscribers; retrieval of a terminal graph run consumes its completion notification.
- Monitor provenance comes from `decidedBy` of a completed successful decision only; a pending escalation shows `awaiting orchestrator`, and dispatch, cancellation, dismissal, and failure claim no decider.

## Trace and replay

[Authoring reference](skills/agent-graphs/references/authoring.md#trace-driven-refinement) covers trace-driven refinement; [README](README.md#agent_graph) describes trace storage.

- `src/graph/trace.ts` owns the per-run trace and runtime inspection log writers; `replay.ts` owns pure trace replay/diff and `replay-command.ts` the `/agent-graph-replay` command. `src/output-file.ts` `sessionArtifactPath`/`createSessionArtifactPath` own exact-session artifact paths.
- Every `agent_graph` run writes `<runId>.trace.jsonl` to the exact-session task artifact area (`<tmpdir>/pi-subagents-<uid>/<encoded cwd>/<sessionId>/tasks/`, 0700 root), kept after settlement. JSONL v1: `header` (runId, startedAt, graph, input, per-node sha256 of canonical `outputSchema`), `node` `added`/`update` lines written only from post-commit publication callbacks, `resume`, `end`, and one `truncated` line at 8 MiB. Traces contain inputs and outputs (node-transcript privacy); NEVER record their path or content in graph history. I/O failure is non-fatal with one warning per session.
- `graphRuntimeTrace` MUST default false and is read at each run start. When on, a system-wide `createActor` `inspect` (nested actors included) writes `<runId>.runtime.jsonl` beside the trace with `{seq, at, type, actor, session, event, value?, tags?}` for `@xstate.event` and `@xstate.microstep` only, NEVER context or event payloads; 64 KiB buffering flushes at run end (a crash may lose the tail); same 8 MiB cap and a separate one-per-session warning.
- `/agent-graph-replay <runId> <graph>` validates the run ID, reads the current session's trace, resolves a saved graph name or `.graph.json`/`.graph.yaml` path, validates it, and folds recorded outputs through the pure planner with no host or model calls into a display-only diff. `fanout`, `bounded_feedback`, `expand`, and `graph` nodes replay atomically from recorded output; ready waves settle in wave order.
