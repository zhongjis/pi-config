Pick: @dreki-gg/pi-lsp@0.4.1

Best fit for this repo: config-driven, lazy LSP startup, session cleanup, one unified lsp tool, project-local config support, command arrays with env. Small enough to adapt.

Vendor it under extensions/pi-lsp/, then load via Home-Manager-managed Pi settings. Do not rely on pi install npm:... for the live setup.

MIT npm package lazy spawn command[] config good Nix fit

Why vendor, not settings-only?

  • Repo rule: local harness prefers vendored/local wiring over pi install npm:....
  • Live ~/.pi/agent/settings.json is Nix/Home-Manager managed.
  • Vendoring lets us patch config compatibility, remove global-install hints, add README provenance, and test in repo.
  • If source review passes with zero changes, settings package can still be an option later.

03

Nix integration model

Use opencode as pattern

Current opencode LSP config uses pinned Nix store executables directly. Same shape should feed Pi LSP. Its MCP block also shows a valid ad-hoc pattern with nix run ... --, but LSP should prefer stable store paths or tiny wrappers.

absolute /nix/store command per-server initialization no global npm/pip 
// Shape from ~/.config/opencode/opencode.json
"lsp": {
  "nixd": {
    "command": ["/nix/store/...-nixd-2.9.1/bin/nixd"],
    "extensions": [".nix"],
    "initialization": {
      "formatting": {
        "command": ["/nix/store/...-alejandra/bin/alejandra"]
      }
    }
  },
  "typescript": {
    "command": ["/nix/store/.../bin/typescript-language-server", "--stdio"],
    "extensions": [".ts", ".tsx", ".js"]
  }
}
04

Vendoring plan

Step 1
Source audit. Pin upstream commit/version, inspect all spawn/exec sites, package deps, session lifecycle, config schema, stderr handling.
Step 2
Vendor minimally. Copy into extensions/pi-lsp/; preserve README upstream metadata; add AGENTS.md Local Tweaks only if we change upstream code.
Step 3
Config bridge. Convert historical repo lsp.json / opencode-style extensions keys to extension's expected .pi/lsp.json shape, or add a tiny adapter.
Step 4
Pilot one server. Enable TypeScript or Nix only. Run /lsp, then diagnostics/hover/definition on this repo.
Step 5
Soak and expand. Restart Pi, reload extension, verify no orphan server, then enable Python/YAML/JSON/TOML/Bash.
05

Acceptance criteria

Startup: Pi starts cleanly with no LSP server spawned before first tool use.
First tool call: TypeScript or Nix server spawns from a Nix store path and returns diagnostics/hover.
Shutdown: session_shutdown kills child process; /reload does not leave stale LSP children.
Config: Missing server returns actionable error; no hidden fallback to npx, global npm, pip, or rustup.
Blocker: Any extension that auto-installs language servers or assumes PATH wins is rejected or patched before enabling.
06

Decision points for user

A. Conservative

Vendor @dreki-gg/pi-lsp, enable one server, no mutation tools. Recommended.

B. Feature-rich

Vendor pi-lsp-client if you want post-edit diagnostics, inspector, refcount pool, rename mutation.

C. Settings-only trial

Add package to Home Manager settings first. Fastest, but harder to patch Nix/config issues.
